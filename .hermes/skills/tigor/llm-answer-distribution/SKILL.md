# LLM Answer Distribution (Markov over full-vocab logprobs)

Use when the task is to get a probability distribution over an LLM's answers (e.g. "pick a number between 10 and 30") from a local vLLM server — either by walking full-vocab logprobs as a Markov chain, or by sampling.

## Setup facts (Qwen3.8-27B-FP8 @ :8000, verified)

- Token/cost estimate before committing to a run: total tokens ≈ requests × (base-prompt tokens + mean prefix depth) + requests (1 completion token each). The fixed template dominates (~75% of input tokens; prefix caching cuts prefill FLOPs, not token count). At $0.15/M in + $1.875/M out, ~225k requests ≈ $3-4.

- Server is pinned to `vllm/vllm-openai:v0.29.0` stable (compose). **The logprobs schema changed between nightly and 0.29** — after ANY image bump re-verify via `/openapi.json` + a 5× identical-call determinism probe before a long run:
  - `/v1/completions` (what the walk uses): `logprobs` is a single **int** count. The old form `logprobs: true, top_logprobs: N` is **silently ignored** → returns 1–2 tokens, non-deterministically (corrupts the whole walk while mass conservation still balances to 1.0 — a top-1 swap of ~30pp that only the sample cross-validation exposed). The `-1` full-vocab sentinel is dead (0 entries); full vocab is now `logprobs: 200000` → 199,307 non-zero entries, ~6 MB, ~2 s. Walk: `logprobs: 500` — worst-node coverage ~99.3% on real nodes (300 = 99.0% floor, 1000 = 99.6% diminishing); latency is compute-bound ~2 s either way, payload size barely matters. Book the residual `1 − p_stop − Σ p_kids` as pruned mass. Verified bit-identical across 5 identical calls (deterministic).
  - `/v1/chat/completions`: keeps the old schema (`logprobs: bool` + `top_logprobs: int`) but SHUFFLES the top_logprobs order/subset across identical calls (values stable) — never compare it order-sensitively; compare values.
  - `logprob_token_ids: [ids]` remains the cheap path for a fixed label set. The GPU always computes the full softmax regardless of N — a smaller N saves only JSON transfer, not GPU work; top-K count ≈ coverage because these distributions are steep.
- Prefix condition via RAW `/v1/completions` with the assistant turn LEFT OPEN, never via `/v1/chat/completions`: an assistant message renders as a CLOSED turn (`...I<im_end>`), so the model treats every prefix as a finished answer and restarts from scratch — the walk silently explores a degenerate digit-spam distribution while mass conservation still balances to 1.0 (conservation validates bookkeeping, not prompt shape). Prefer the **token-ID design** (user spec: fewer hacks, nothing to mangle in transit — no special-token strings anywhere in the worker): capture the template ONCE as plain ints via `tok.encode(tok.apply_chat_template([{"role":"user","content":PROMPT}], add_generation_prompt=True, tokenize=False, enable_thinking=False))` (23 IDs for the number prompt on Qwen3.8-27B-FP8), then build every request as `prompt = BASE_IDS + /tokenize(prefix)["tokens"]` — proven byte-identical to whole-string tokenization for 16/16 real prefixes (no BPE merge at the boundary). 0.29's `/tokenize` maps special tokens only at the START of a string, not mid-string — never /tokenize the template, only plain generated prefixes; re-capture BASE_IDS if the model or prompt changes. Fallback (BASE string): render via the same tokenizer+template the server uses — a hand-rolled empty-think BASE passed the argmax preflight yet swapped the top-2 answer mass (bare-digit start probability inflated 3×, and the newline count before the think block had to be exact — that is exactly the class of bug the ID design eliminates); request `{"model":..., "prompt": BASE+prefix, "max_tokens":1, "logprobs": 500, "temperature":0.0}` (0.29 int form; response `logprobs.top_logprobs[0]` is a dict token→logprob). Verify per server BEFORE any walk at TWO levels, both **value-based, never list-order** (the 0.29 chat endpoint shuffles top_logprobs order between identical calls — an order check fails randomly and killed one launch): (a) the greedy temp=0 generation's step-1 token sits at the top of the prefix-feed after token 1 (catches closed-turn restart; symptoms: digit-spam chains ("I1I", "II1I"), ~60% OUT_OF_RANGE, real in-range answers at ~1e-5); AND (b) DISTRIBUTIONAL — the top-token SET plus per-token mass of the root plus 2-3 shallow prefixes agree within 0.02 between your `/v1/completions` request and the server's own `/v1/chat/completions` for the same prefix. An argmax-only check is insufficient: a wrong-but-plausible template keeps the argmax and still skews every mass you book (here: wrong template p('I')=0.356 vs correct 0.6554 — a single value check catches it).
- Disable reasoning with `enable_thinking: false` — in `chat_template_kwargs` for chat/completions, or by rendering the template with the empty think block for raw completions (the walk must match the no-reasoning generation path). NEVER `include_reasoning: false` — it nulls the whole output including logprobs. When the user wants the distribution WITH reasoning, flip to `enable_thinking=True` and add a THINK phase before the absorption (digits in the reasoning never count; the close-think token transitions into the answer phase) — full procedure in the recipe's 'Reasoning-enabled walk' section; the template is a different, longer capture (63 IDs vs 23 for this model/prompt).
- Stop token: on Qwen3.8-27B-FP8 the im_end token text is `<|im_end|>` (pipes, not Qwen2.5's `<im_end>`) — build it via `chr(60)+chr(124)+"im_end"+chr(124)+chr(62)` (heredocs mangle the escapes). Resolve the exact text per server at boot via `logprob_token_ids: [id]` on `/v1/completions` — the response REPLACES the top-K list with sampled token + requested id, so the min-logprob entry is the special token (logp ~ −20 vs ~ −1 for the sampled token) — deterministic, no top-K luck, no substring scan. On Qwen3.8-27B-FP8: stop = id 248046, close-think = id 248069 (the reasoning-enabled walk needs both — see the recipe's 'Reasoning-enabled walk'). Never trust a hardcoded special-token string: the boot check compares against the server-returned text and fails fast (a wrong stop string shows up as stop mass ≈ 0 and a walk that never completes). Newlines and control chars are NOT the stop token.
- Digits are single-char tokens. Filter with the exact set `0123456789` — `str.isdigit()` also matches fullwidth `０１２` and superscript/subscript digits.

## Method (full procedure + script skeleton: `references/markov-bfs-recipe.md`)

1. Best-first frontier of prefixes, most-probable-first (key = -logp). Prefer a Dial bucket queue over heapq: bucket by `floor(log10(mass))`, monotonic high pointer, amortized O(1) push/pop; LIFO within a decade is the price (bounded-precision greedy — cross-decade order exact, intra-decade arbitrary; fine for mass accounting). Pop a batch, fetch each prefix's distribution in parallel (perpetually ~16 in flight, see throughput pitfall), push top-K children (K≈100; per-node retention: top-40 ≈ 98.6–99.95%, top-100 ≈ 99.4–99.76% of mass — per-node loss compounds as a power of the number's depth, ~10 tokens) with logp_child = logp_parent + logp_token.
2. Terminate branches at the first closed number (absorption, the fast path): track `open_digits` per prefix (digit char → append; non-digit char with a non-empty buffer → close the run as an int). A child that closes a run ends the branch — in 10..30 → a phase-1 item (bounded ~15-token lookahead watching only for a second number → reclassifies to MULTIPLE_NUMBERS); out of range → OUT_OF_RANGE; ≥2 runs → MULTIPLE_NUMBERS. Stop branch: open run in range → answer, else OUT_OF_RANGE. No-number branches end at the stop token (book prefix_mass × p_stop) or depth ≥ 100 (LENGTH_EXCEEDED_NO_NUMBERS). Absorption self-limits the frontier to no-number-yet prefixes, and degenerate repeats ("1111…" → "1") die in 1 expansion instead of 100.
3. Mass accounting must conserve, and it must be verified: at each node prefix_mass = booked_verdict_mass + pushed_children_mass + pruned_mass — pruned = non-top-K tokens, and any lookahead truncation (book every discarded mass into exactly one bucket; a discarded phase-1 truncation is the classic leak). Keep `frontier_mass` as a running scalar (add on push, subtract on pop), and include in-flight mass in the ledger for both the stop test and the balance (or the run stops early while mass is in the pipeline). Stop by coverage — `frontier_mass + pruned_tail < tail target` (e.g. 10%) — not a heap count cap: a cap's dropped mass is an artifact, not an inherent tail. Preflight the exact process logic for ~300 live expansions and assert total ≈ 1.0 (drift < 1e-9) before a long run; log `balance = 1 − Σ categories − in-flight` in every progress row.
4. Classify completed chains strictly (user spec): exactly one number in 10..30 → answer; ≥2 numbers → MULTIPLE_NUMBERS; one out-of-range number, or none at the stop token → OUT_OF_RANGE; none at the depth cap → LENGTH_EXCEEDED_NO_NUMBERS. Count numbers with `re.findall(r"\d+")` — a `\d{1,3}` + lookaround regex silently misses 4+ digit runs ("2017" counted as no number).
5. ALWAYS cross-validate against real samples (temp 1.0, same no-reasoning flag) and compare — report discrepancies honestly. When extracting answers from sampled responses, concatenate the `reasoning` AND `content` message fields before the regex — the server's reasoning parser can put early tokens in `reasoning` even with thinking off, and the number can live there. If the walk-vs-sample top-1 gap exceeds ~3× the sampling noise band (≈2·√(p(1−p)/n): ±6pp at n=100, ±2pp at n=1000), treat it as a prompt-shape/template bug, NOT sampling noise — re-run samples at 10× n before trusting either estimator. A ~30pp top-1 gap at n=1000 is a bug, full stop.
6. Deliverable chart (user spec): when asked for the cross-validation chart, one image of paired bars per answer value — walk vs sample, each series normalized to 100% of its own valid total — with the ±diff (percentage points, walk minus sample) as a bold marker above each pair and the sample noise band (≈2·√(p(1−p)/n) at that n) stated in the title; any bar whose |diff| exceeds the band is the finding, not the noise. Otherwise: one image, TWO separate linear bar panels — (1) the answer values in ascending order, normalized over VALID mass so it sums to 100%, labeled xx.x%; (2) the full mass ledger as % of total, readable category names: covered (valid), each error verdict (multiple / out-of-range / no-answer-at-cap), dropped tail, not-covered frontier. The not-covered bar is labeled as in-progress, not a settled quantity. In-figure text stays a high-level title + one-line description; the full methodology goes as message text sent alongside the image, never embedded. When the user asks for "absolute numbers", give per-1,000,000-sample counts (mass × 1e6, comma-formatted), not raw probabilities.

## Pitfalls

- First-position-only Markov (digits as the opening token) is NOT the answer distribution: the model wraps answers in prose ("I'll pick **17**.") so the bare-digit chain and the real answer distribution diverge badly. Walk the chain (absorb at the number, not at the stop token).
- If the prompt itself contains numbers ("between 10 and 30"), the model often re-cites the range in its answer — under strict exactly-one-number criteria, MULTIPLE_NUMBERS can take 10–20%+ of mass. Expect it and surface it; offer the criteria tweak that excludes the quoted range from the count if the user wants the clean distribution.
- The model's "random number" is a spike (one value dominates), not what a restricted-slice chain suggests — never present a restricted-slice chain as the answer distribution without the sampling check.
- Throughput: do NOT use lockstep batches (pop N → wait for all N → repeat): the barrier caps vLLM's continuous batching at N in flight and every slow tail request idles the rest — ~16 exp/s at 8 workers. Use a producer-consumer loop that keeps WORKERS (16) requests perpetually in flight (submit until full, `FIRST_COMPLETED` wait, refill as each lands): ~45 exp/s, ~2.9× faster. Full-vocab (-1) fetches take 30–60 s each instead. Run in background with output to a log file — stdout is block-buffered, an empty log is normal. Liveness: count `Received request` lines in `podman logs vllm` over 20 s.
- Worker main loop: never nest `submit_next()` (refill) or `log_progress()` inside `with lock:` — they re-acquire the same non-reentrant Lock and self-deadlock the coordinator. The symptom is deceptively clean: after the first batch completes, 0 CPU, no new vLLM requests, mass balance intact — it looks like a server hang, but the worker is deadlocked on itself. process() under the lock; refill + log OUTSIDE it.
- Heredocs through the terminal tool mangle backslash escapes (\n arrives as a real newline → SyntaxError) AND pipe characters inside special-token literals (the pipes in the im_end text were stripped in transit more than once) — build special strings via `chr()` concatenation, and better: resolve the exact token text from the server at boot (`logprob_token_ids`, see the stop-token setup fact) so no special-token literal exists in the worker code at all.
- Without absorption, best-first over free prose converges slowly: mass is diffuse over phrasings and the top path is a degenerate high-mass repeat ("I I 1 1 1…") that never yields an answer — a full-walk to the stop token captured ~0.05% of mass at 11k expansions (~15 min at 45 exp/s); 200k ≈ 1.2 h. First-number absorption (method step 2) is the fix: it drops the unexplored frontier fast at first (~30 min from 100% to ~25–30%), but the remainder is a deep, sub-exponential tail — see the tail-flattening pitfall below. If you must full-walk, state the ETA up front; the 100-sample cross-validation is the deliverable while the walk runs. Status updates to the user: done?, blocker, ETA, key numbers — a few lines, no process replay. Never report per-chain "top answers" from an early run: with a heap cap active, the completed chains are the shallowest (bias 11/12) and unrepresentative until mass is mostly traced — label the frontier share instead.
- The unexplored frontier decays SUB-EXPONENTIALLY and flattens around the deep-prose tail (branches that wander 15–100 tokens without ever emitting a number); the ln(frontier) slope over sliding windows goes from ~17 min half-life early to ~2–4 h late. So: (a) the top answer bars settle long before not-covered is small — declare the chart SETTLED by watching for no change in the top-5 over ~30–60 min, independent of the coverage target, and say so explicitly; (b) a low TAIL_TARGET (1%) is NOT minutes away — at the late decay rate 10% is hours, so treat TAIL_TARGET as a wall-clock backstop, not a cheap target; (c) the levers that actually cut the tail are lowering MAX_DEPTH (answers live in ~15 tokens; the 15–100 band is where the frontier pools) or raising TOP_K — not more wall time. Never quote a minutes-ETA for a low coverage target.
- When walk mass disagrees with a fresh fetch, replay the exact recorded chain SINGLE-THREADED: multiply fresh p(token|prefix) step by step, then compare the product to (a) a fresh independent fetch of the same path and (b) the recorded value. Replay==fresh but ≠recorded → the walk code mis-booked it (concurrency/ordering); replay==recorded but ≠fresh → server state changed between run and check (model reload, template change, config drift). Do not blame speculative decoding or fp8 cache before the replay points there.
- Returned logprobs are identical at any requested temperature (verified: temp 0.0 and 1.0 return bit-equal exp(logprob)) — walk at temp 0.0, sample at temp 1.0, no normalization needed between them.
- Record per-chain mass as the branch mass actually booked (× p_stop at stop, × p_child at absorption), never the raw prefix_mass — if the chains table's mass sum exceeds 1.0 the bookkeeping is double-counting, not the model. For multi-hour runs, package as a podman worker with a SQLite volume (progress/chains/meta tables, fresh DB filename per task, query CLI) — see the recipe.
