# LLM Answer Distribution (Markov over full-vocab logprobs)

Use when the task is to get a probability distribution over an LLM's answers (e.g. "pick a number between 10 and 30") from a local vLLM server — either by walking full-vocab logprobs as a Markov chain, or by sampling.

## Setup facts (Qwen3.8-27B-FP8 @ :8000, verified)

- Full-vocab logprobs need `--max-logprobs -1` in the server command (default cap 20; `top_logprobs: -1` otherwise 400s). Request: `logprobs: true, top_logprobs: -1` → all 248,320 tokens, ~21 MB JSON, ~4.7 s per call. `logprob_token_ids: [ids]` is the cheap path for a fixed label set. For heap walks do NOT request `-1`: `top_logprobs: 500` is ~16 KB / 0.33 s per call (~500× faster) since only the top-K children and the stop token matter — book the residual `1 − p_stop − Σ p_kids` as pruned mass; use `-1` only for arbitrary-token lookups. vLLM has no cumulative-probability logprob mode — `top_logprobs` is a count or -1 (serving filter: `return_all or top_logprobs == -1 or i < top_logprobs`) and the GPU always computes the full softmax regardless of N, so dropping the tail 'before sending' saves only JSON transfer, not GPU work; top-K count ≈ coverage because these distributions are steep.
- Prefix condition via RAW `/v1/completions` with the assistant turn LEFT OPEN, never via `/v1/chat/completions`: an assistant message renders as a CLOSED turn (`...I<im_end>`), so the model treats every prefix as a finished answer and restarts from scratch — the walk silently explores a degenerate digit-spam distribution while mass conservation still balances to 1.0 (conservation validates bookkeeping, not prompt shape). Build the prompt as the chat template rendered with `add_generation_prompt=True` + `enable_thinking=False` (ends in the empty think block) with the prefix appended, and request `{"model":..., "prompt": BASE+prefix, "max_tokens":1, "logprobs": K, "temperature":0.0}` (top_logprobs maps to `logprobs`; response `logprobs.top_logprobs[0]` is a dict token→logprob). Verify per server BEFORE any walk: the greedy temp=0 generation's step-1 token must sit at the top of the prefix-feed distribution after token 1 — if the greedy continuation token is absent from top-K, the prompt shape is wrong; symptoms: digit-spam chains ("I1I", "II1I"), ~60% OUT_OF_RANGE, real in-range answers at ~1e-5 while 100-sample ground truth shows a 60% spike.
- Disable reasoning with `enable_thinking: false` — in `chat_template_kwargs` for chat/completions, or by rendering the template with the empty think block for raw completions (the walk must match the no-reasoning generation path). NEVER `include_reasoning: false` — it nulls the whole output including logprobs.
- Stop token: on Qwen3.8-27B-FP8 the im_end token text is `<|im_end|>` (pipes, not Qwen2.5's `<im_end>`) — build it via `chr(60)+chr(124)+"im_end"+chr(124)+chr(62)` (heredocs mangle the escapes). Always verify per server by scanning the head distribution for 'im_end' (logp ≈ −11 here); a wrong stop string shows up as stop mass ≈ 0 and a walk that never completes. Newlines and control chars are NOT the stop token.
- Digits are single-char tokens. Filter with the exact set `0123456789` — `str.isdigit()` also matches fullwidth `０１２` and superscript/subscript digits.

## Method (full procedure + script skeleton: `references/markov-bfs-recipe.md`)

1. Best-first frontier of prefixes, most-probable-first (key = -logp). Prefer a Dial bucket queue over heapq: bucket by `floor(log10(mass))`, monotonic high pointer, amortized O(1) push/pop; LIFO within a decade is the price (bounded-precision greedy — cross-decade order exact, intra-decade arbitrary; fine for mass accounting). Pop a batch, fetch each prefix's distribution in parallel (perpetually ~16 in flight, see throughput pitfall), push top-K children (K≈100; per-node retention: top-40 ≈ 98.6–99.95%, top-100 ≈ 99.4–99.76% of mass — per-node loss compounds as a power of the number's depth, ~10 tokens) with logp_child = logp_parent + logp_token.
2. Terminate branches at the first closed number (absorption, the fast path): track `open_digits` per prefix (digit char → append; non-digit char with a non-empty buffer → close the run as an int). A child that closes a run ends the branch — in 10..30 → a phase-1 item (bounded ~15-token lookahead watching only for a second number → reclassifies to MULTIPLE_NUMBERS); out of range → OUT_OF_RANGE; ≥2 runs → MULTIPLE_NUMBERS. Stop branch: open run in range → answer, else OUT_OF_RANGE. No-number branches end at the stop token (book prefix_mass × p_stop) or depth ≥ 100 (LENGTH_EXCEEDED_NO_NUMBERS). Absorption self-limits the frontier to no-number-yet prefixes, and degenerate repeats ("1111…" → "1") die in 1 expansion instead of 100.
3. Mass accounting must conserve, and it must be verified: at each node prefix_mass = booked_verdict_mass + pushed_children_mass + pruned_mass — pruned = non-top-K tokens, and any lookahead truncation (book every discarded mass into exactly one bucket; a discarded phase-1 truncation is the classic leak). Keep `frontier_mass` as a running scalar (add on push, subtract on pop), and include in-flight mass in the ledger for both the stop test and the balance (or the run stops early while mass is in the pipeline). Stop by coverage — `frontier_mass + pruned_tail < tail target` (e.g. 10%) — not a heap count cap: a cap's dropped mass is an artifact, not an inherent tail. Preflight the exact process logic for ~300 live expansions and assert total ≈ 1.0 (drift < 1e-9) before a long run; log `balance = 1 − Σ categories − in-flight` in every progress row.
4. Classify completed chains strictly (user spec): exactly one number in 10..30 → answer; ≥2 numbers → MULTIPLE_NUMBERS; one out-of-range number, or none at the stop token → OUT_OF_RANGE; none at the depth cap → LENGTH_EXCEEDED_NO_NUMBERS. Count numbers with `re.findall(r"\d+")` — a `\d{1,3}` + lookaround regex silently misses 4+ digit runs ("2017" counted as no number).
5. ALWAYS cross-validate against N≥100 real samples (temp 1.0, same no-reasoning flag) and compare — report discrepancies honestly.

## Pitfalls

- First-position-only Markov (digits as the opening token) is NOT the answer distribution: the model wraps answers in prose ("I'll pick **17**.") so the bare-digit chain and the real answer distribution diverge badly. Walk the chain (absorb at the number, not at the stop token).
- If the prompt itself contains numbers ("between 10 and 30"), the model often re-cites the range in its answer — under strict exactly-one-number criteria, MULTIPLE_NUMBERS can take 10–20%+ of mass. Expect it and surface it; offer the criteria tweak that excludes the quoted range from the count if the user wants the clean distribution.
- The model's "random number" is a spike (one value dominates), not what a restricted-slice chain suggests — never present a restricted-slice chain as the answer distribution without the sampling check.
- Throughput: do NOT use lockstep batches (pop N → wait for all N → repeat): the barrier caps vLLM's continuous batching at N in flight and every slow tail request idles the rest — ~16 exp/s at 8 workers. Use a producer-consumer loop that keeps WORKERS (16) requests perpetually in flight (submit until full, `FIRST_COMPLETED` wait, refill as each lands): ~45 exp/s, ~2.9× faster. Full-vocab (-1) fetches take 30–60 s each instead. Run in background with output to a log file — stdout is block-buffered, an empty log is normal. Liveness: count `Received request` lines in `podman logs vllm` over 20 s.
- Heredocs through the terminal tool mangle backslash escapes (\n arrives as a real newline → SyntaxError). Build special strings via `chr()` concatenation.
- Without absorption, best-first over free prose converges slowly: mass is diffuse over phrasings and the top path is a degenerate high-mass repeat ("I I 1 1 1…") that never yields an answer — a full-walk to the stop token captured ~0.05% of mass at 11k expansions (~15 min at 45 exp/s); 200k ≈ 1.2 h. First-number absorption (method step 2) is the fix: ~5–15 min to a 10% unexplored tail. If you must full-walk, state the ETA up front; the 100-sample cross-validation is the deliverable while the walk runs. Status updates to the user: done?, blocker, ETA, key numbers — a few lines, no process replay. Never report per-chain "top answers" from an early run: with a heap cap active, the completed chains are the shallowest (bias 11/12) and unrepresentative until mass is mostly traced — label the frontier share instead.
- Record per-chain mass as the branch mass actually booked (× p_stop at stop, × p_child at absorption), never the raw prefix_mass — if the chains table's mass sum exceeds 1.0 the bookkeeping is double-counting, not the model. For multi-hour runs, package as a podman worker with a SQLite volume (progress/chains/meta tables, fresh DB filename per task, query CLI) — see the recipe.
